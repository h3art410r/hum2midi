# 转谱链路 Review 设计

这份文档记录当前“音频 → 旋律 MIDI”的实验边界。它不是产品承诺，目的是让每次模型替换都能做可归因的 A/B。

## 问题拆分

同一段人声里有三个不同问题：

1. **音频理解**：是否有人声、几段、哪里停顿、整体音高走向。
2. **音符测量**：每次起音的时间、持续时间、基频和滑音。
3. **音乐意图**：用户实际哼出的音，还是用户脑中的标准曲谱。

通用多模态模型对第一项有能力，但第二项需要很细的时间分辨率；第三项没有参考音频或调性时无法从录音唯一推断。把三个问题塞进一个“请输出 MIDI”的 Prompt，会把不同误差混在一起。

## 当前架构

```text
原始录音
   ├─ Qwen Omni：独立音频理解（必做，输出 contour）
   └─ TranscriptionEngine：只负责逐音 MIDI
         ├─ dsp-yin（可重复基线）
         ├─ klangio-vocal-cloud（可选专业云端）
         └─ tencent-vocal-cloud（可选大陆云端）
                    ↓
              Melody IR
                    ↓
              风格模型 / MIDI 渲染
```

`TranscriptionEngine` 是唯一需要替换的边界。引擎失败会显示失败；不会因为云端不可用而悄悄切到另一个引擎。`auto` 只是启动时选择已配置的 provider，不是运行时 fallback。

## A/B 测量协议

所有候选必须使用同一份规范化 WAV，并保存：

- 音符数、起音时间误差、持续时间误差；
- 整数 MIDI 音高准确率和 `pitch_cents` 误差；
- 句界和整体 contour 是否一致；
- 端到端延迟、失败率、单次费用；
- 盲听样本，不把“音符更多”当作准确。

Qwen Omni 的候选音高实验在 `docs/probe_multimodal_note_ranking.py`。它现在随机打乱 A/B/C 候选并重复多次，输出每次选择和共识，专门检查位置偏置。这个实验只用于判断模型是否能做窄任务，不进入主流程。

## 目前结论

- Qwen Omni 可以稳定给出粗粒度旋律描述，但直接逐音 JSON 和候选半音选择都没有达到生产级稳定度。
- YIN、Basic Pitch、pYIN、Praat 对当前录音的整数轮廓基本相互印证；`pitch_cents` + Pitch Bend 保留了人声偏离钢琴半音的细节。
- Klangio `vocal` 和腾讯 `vocalMidi` 都是下一项有明确区分度的云端对照。配置对应密钥后才能真实测试；没有密钥时不能宣称任一条路线更准。腾讯接口要求第三方通过 HTTPS URL 读取音频，因此应用只提供带随机 job id 的临时规范化 WAV 路由，不会把本地路径或密钥返回给前端。
- 如果负责人要求“听起来像标准《小星星》”，那是意图校正问题，需要参考曲谱/调性或额外的云端音乐知识步骤；不能仅凭当前人声测量保证。

## 2026-09-17：旋律语义记忆 A/B

此前的统计/规则修正层已移除。它会把“重复音对、调内音、连续下行”等统计假设直接写进 MIDI，约束过强，可能把真实旋律改错。

当前候选层 `app/melody_semantic.py` 只把声学测得的 MIDI 音高、相对半音序列、起音和时值交给云端文本模型。Prompt 明确禁止歌名、外部资料和联网，只允许模型依靠已有音乐记忆判断是否存在“非常相似”的常见旋律。模型必须同时返回 `similarity`、简谱和等长 MIDI 音高；只有 `similarity` 与 `confidence` 都不低于 0.90 时才替换音高，起音、时值、句界、音符数量始终沿用原始测量。没有高相似匹配、返回不合法或模型调用失败时，直接保留 measured MIDI。

这条路径使用 `QWEN_MELODY_MODEL=qwen-plus`，与 Funk/Lofi 风格模型分开配置；它的结果和是否改音会写入 `melody_semantic` 诊断，页面仍同时保留 A（声学基线）和 B（语义候选）试听。此前对当前录音的离线试验中，Qwen Plus 能识别出 14 音的常见简谱并返回修正序列；Flash 给出不相似，因此默认不会采用 Flash 的猜测。该结果仍需用多段新录音继续做盲测，不能把模型自报置信度当作普遍准确率。
